# ancs-bridge 0.2.0

## Changes since v0.1.0

- Setup uses simpler JSONL confirmation for terminal users and desktop frontends.
- Status reports the live BlueZ device name and classifies a missing configured bond as `configured-device-not-bonded`.
- ANCS recovers passively after daemon restarts. Disconnected-phone refreshes back off, and failed ANCS streams wait before retrying ([#7](https://github.com/mateuszkowalczyk/ancs-bridge/pull/7)). This reduces retry churn; it does not establish what caused the intermittent CPU spike in [#4](https://github.com/mateuszkowalczyk/ancs-bridge/issues/4).
- The daemon can receive notifications when BlueZ exports live ANCS characteristics but still reports `ServicesResolved=false`. It checks for a live subscription on the configured bond before reporting `ready`.
- Optional `notifications.ignore_apps` exclusions suppress duplicate desktop delivery by exact iOS bundle ID. Repair and re-pair preserve the list ([#5](https://github.com/mateuszkowalczyk/ancs-bridge/pull/5)).
- New and replacement notifications request the themed `phone` application icon. Display depends on the notification server and icon theme ([#9](https://github.com/mateuszkowalczyk/ancs-bridge/pull/9)).
- The Arch recipe pins and verifies an immutable source archive. The README documents source installation from the release checkout instead of the unavailable AUR package ([#2](https://github.com/mateuszkowalczyk/ancs-bridge/pull/2), [#10](https://github.com/mateuszkowalczyk/ancs-bridge/pull/10)).
- Update Tokio to address [RUSTSEC-2026-0386](https://rustsec.org/advisories/RUSTSEC-2026-0386).

## Upgrading and frontend compatibility

The machine API still reports `apiVersion: 1`, but **setup confirmation is not wire-compatible with v0.1.0**. `confirmation-request` no longer includes `requestId`. Earlier confirmation commands containing `requestId` or `accept` are rejected. Send one of these JSON objects per line on setup stdin:

```jsonl
{"v":1,"command":"confirm"}
{"v":1,"command":"reject"}
{"v":1,"command":"cancel"}
```

`cancel` is unchanged. Frontends should use the daemon release version to select a compatible setup protocol rather than relying on `apiVersion` alone. Treat `deviceName` as a display label, not an identifier, and handle `configured-device-not-bonded` as a pairing repair case rather than a generic BlueZ error.

The config schema and systemd user unit are unchanged. Existing configuration does not require migration or re-pairing just to upgrade. Downgrading disables app exclusions; older binaries may remove the optional policy when rewriting configuration.

## Install on Arch Linux

Use Arch package revision `0.2.0-2` on rolling Arch. It fixes the Rust 1.100
build failure in the original recipe ([#17](https://github.com/mateuszkowalczyk/ancs-bridge/issues/17));
the daemon still reports version `0.2.0`. Follow the
[source-install steps](https://github.com/mateuszkowalczyk/ancs-bridge/blob/arch-0.2.0-2/README.md#install-from-source-on-arch-linux).
Installation does not pair your phone or enable or start the service. If
upgrading an already running service, restart it to load the new binary.
